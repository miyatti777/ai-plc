# ppm-scan（外から案件の候補を集める）

> 論理名: SKL_plc_scan ／ 層: ポートフォリオ層 ／ 書くもの: 収集メモ1つだけ

「Notion と Slack も見て仕事を拾って」「仕事の一覧が足りない」と頼まれたときに、**一度だけ**集める。結果は未承認の候補として収集メモに保存し、チャットに返す。定期の見張り・Slack の自動収集は作らない。

- **似たスキルとの違い:** `ppm-collection` は**手元の** Registry と Layer から既にある案件を探す。こちらは Notion・Slack など**外**から、まだ一覧に無い候補を拾う
- **TODO への反映はこのスキルの外:** 候補をあなたの TODO 管理へ入れるかは、メモを見て人が決めて行う（同梱の日次の入口を使うなら、選んだ候補を `/ppm-todo` で TODO の一覧へ）。案件として進めるものは `/01-collection`、今は着手しないものは `/ppm-someday` へ（どちらも人が選んでから）

## 入力と範囲

- 対象の Notion ページ・ワークスペース、Slack ワークスペース・本人、期間、除外先。この会話で指定された範囲を使い、決まっていないワークスペース・本人は推測しない
- 期間の指定が無ければ、基準日を含む直近30暦日を初期案にし、使った期間を表示する。Slack の日付の境界に合わせ、検索式と対象期間の差をなくす
- 比べる相手（任意）: 利用者が渡した今の仕事の一覧（TODO 管理の写しなど）、前回の収集メモ、取得済みの資料。渡されなければ照合は「既存の一覧との対応: 未確認」とする
- 保存先: 指定が無ければ日付を確かめて `Flow/YYYYMM/YYYY-MM-DD/ppm-scan/` に今回の収集メモを作る。親フォルダがあるか確かめてから作り、既存のメモは上書きせず別名にする
- Slack は公開チャンネルの本人の発言から始める。DM・非公開チャンネル・添付・別のワークスペースを含めるには、その対象を名指しした追加の指示が要る。雑談は候補から外す。取得の道具の側でも公開に限った検索を使う
- 取得済みの資料だけで照合し直すこともできる。その場合は新しく取得した件数0とし、資料の取得日時と照合し直した日時を分けて書く

範囲の指定が足りないときは、要る点だけを聞き、渡された資料の整理を先に進める。接続しているアカウントの表示名・本人の ID が指定の範囲と合うか確かめ、要る ID 以外のプロフィール情報は保存しない。

## 集めて照らす

1. `date +%Y-%m-%d` を単独で実行し、基準日とタイムゾーンを決める。比べる一覧が渡されていれば読み、既にある親の案件をつかむ。ここで全 Layer の YAML を走査しない
2. 使える読み取りの道具を確かめる。接続済みの Notion・Slack の connector や API が**使えるものだけ使い**、各道具の検索・取得・権限の説明に従う。存在しない道具の名前や接続の成功を仮定しない。使えるものが無ければ、その旨を返して止める
3. Slack は本人の ID と期間で絞って検索し、各ページを少しずつ読む。候補になりそうな依頼・約束は、関連するスレッドの親と返信を確かめる。返信の中の担当・完了・引継ぎも読むが、関係しない別のチャンネルへ広げない
4. Notion は指定のページと、そこから辿れる業務のページ、Slack の中にある許可範囲内のリンクを読み、今の Status・担当・期限・本文・更新日時を照らす。DB はスキーマを確かめてから、本人の担当や関連する案件に絞って読み取りで照会する。検索の入口が使えなければ既知の URL から取得する。接続先が指定の範囲内でも、全ページを本人の担当とは扱わない
5. ページングの終わり、打ち切り、取得件数、検索式・対象ページ、取れなかったものを記録する。各情報源の取得エラーは1回だけ再試行し、解消しなければ理由と再開のしかたを1行で示して、取得できた分で続ける。情報が無いことと、取得できないことを区別する
6. 下の基準で候補を案件1行にまとめる。比べる一覧と、名前だけでなく目的・相手・成果物・本人の役割を比べる。手元の Layer との対応が要る候補だけ、`/ppm-collection` で照らすよう添える。全 YAML のタスクを案件一覧にしない

## 候補の判断

- 本人が依頼を受けた・約束した仕事、今の担当の記載と最近の動きが合う仕事は追加の候補にする。発言・参加・提案だけを担当の引き受けとみなさない
- 主担当、判断の支援・レビュー、委任・相手待ち、担当不明を区別する。別の人の実装は本人の実装の TODO にせず、本人に残る判断・確認があればその行動を示す
- 同じ目的の機能・小さなタスクは親の案件へまとめる。既存の一覧の行に当たるなら統合の候補とし、名前が似ているだけで同じ案件と決めない。関係が分からなければ本人への確認に残す
- はっきりした完了の返信や、対象に合う今の Done は、新しい未完了の候補から外す。ただし一部の完了を案件全体の完了へ広げない。日付の新しさだけで別の対象の情報を優先せず、食い違う根拠は両方示す
- 古い担当・期限・未完了のチェックだけなら、鮮度の確認の候補にする。返事が無いことを、今も未解決の証拠にしない。検索で見つからないことを削除の根拠にしない
- 本人が残すと決めている案件は、古い期限だけで外さない。本人の緊急度の判断・今日の優先度・次の日の計画・未完了の扱いを代わりに決めない

## 保存する収集メモ

先頭に、収集日、資料の取得日時、対象・期間・件数・取れなかったものと「候補は未承認」を書く。候補ごとに次を残す。

| 項目 | 内容 |
|---|---|
| 候補ID・案件名 | 1案件1行。内部のタスク番号ではなく、対象と行動で書く |
| 本人の役割 | 主担当／判断の支援・レビュー／委任・相手待ち／担当不明 |
| 次の行動 | 根拠から分かる行動。未確認なら確認事項として分ける |
| 期限・相手待ち | 明示された期限・待つ相手。書かれていなければ未確認 |
| 根拠 | Notion・Slack へのリンク、発言・更新日時、要るだけの要約 |
| 照合 | 根拠の上で未完了／完了／鮮度の確認／食い違い、既存の一覧との対応 |
| 提案 | 追加／既存へ統合／除外／本人に確認。確定と推定を分ける |

外した主な情報と理由も残す。本文は要る分だけにし、道具の出力の全体・署名つきの URL・認証情報・鍵・トークン・パスワード・口座番号は保存しない。メモを置くフォルダが git で共有されるなら、実名・連絡先を書いてよいかを利用者の決まりに合わせる（分からなければ聞く）。

## 返す（ここで止まる）

- チャットには、候補・確認事項・収集メモのパスを返す。このスキルは TODO の一覧・backlog・Registry・Notion・Slack を変えない
- 候補を一覧へ入れるかどうかは利用者が決め、利用者の TODO 管理で行う。過去の別の提案への承認を、新しい候補への承認として使わない
- 案件として始める・既存の案件の続きにする候補は、次の入口を添える（実行は利用者が選んでから）: 手元の似た案件を探す `/ppm-collection <候補の言葉>`、新しく始める `/01-collection Goal: <候補>`、今は着手しない `/ppm-someday <候補>`
- connector が無い・権限が足りないときは「未取得」と返す。取得済みの許可された資料があれば、それだけで照らし直せる
