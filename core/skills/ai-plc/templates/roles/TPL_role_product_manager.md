> 🏷️ **Type:** role template (focus strategy) — Stage 1（/01-collection）のFocus Strategyで選択

対象Goal: プロダクト開発・改善、新サービス立ち上げ、機能追加、ユーザー体験向上。
権限: 調査・リサーチ、企画書・PRD作成は可。実装（DB作成・コード実行）は不可。最終承認はステークホルダー。

## 分解パターン

フェーズ構造: Discovery（調査・検証）→ Design → Delivery（実装・提供）→ Measure & Learn。MVP思考で最小単位の価値提供と早期フィードバックループを優先する。

| Phase | 典型タスク |
| --- | --- |
| Discovery | ペルソナ定義、インタビュー、競合調査、仮説立案 |
| Design | 要件定義、UI/UX設計、技術選定、MVP範囲決定 |
| Delivery | 実装、テスト・QA、リリース、ドキュメント |
| Measure & Learn | KPI設定、フィードバック収集、データ分析、改善仮説 |

- SubLayer化: プロダクト企画（Complex時は必須でSG0として独立展開。Taskにしない）、異なるペルソナ向け機能、単独でMVPとして成立する機能群、技術ドメイン分離
- Task化: 横断的な技術決定、統合・デプロイ系、検証・QA系、運用・ドキュメント系
- 留意: MVP精神で最小単位から分解し、仮説検証を優先する。企画は必ずSubLayerとして深く検討する

## ロール固有検証（system §18拡張）

| Level | 確認観点 |
| --- | --- |
| L1 | 各主張にデータ・事例・インタビュー結果の裏付けがあるか、ペルソナ像が具体的で矛盾がないか |
| L2 | 課題→ソリューション→価値の流れが自然か、MVP定義が最小構成で仮説検証可能か |
| L3 | 意思決定者が読んでGO/NO-GO判断できるか、失敗シナリオとリカバリープランが明示されているか |

品質ゲート: Discovery完了（ペルソナ確定+課題裏付け+競合比較）→ 企画書承認（Mob: ステークホルダーGO判断）→ Delivery完了（要件通り実装+KPI計測準備）。

## ロール固有NFR（system §19拡張）

| NFR領域 | 確認観点 |
| --- | --- |
| 市場適合性 | ターゲット市場のニーズに合致しているか（裏付けなしの「良さそう」は不可） |
| ユーザー価値 | エンドユーザーにとっての価値が明確か |
| ROI | コスト見積りを含め投資対効果が説明できるか |
| 競合優位性 | 競合分析に基づく差別化があるか |
