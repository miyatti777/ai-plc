# GOBOLD — Goalへの最小利用・学習導線を検討する選択式基準

対象Taskに本人が `review_profile: gobold` を明示選択した場合だけ適用する。今回のGoal/GAP・計画成果物への直接選択も、その成果物と現在のレビューに限って扱い、出典と対象を渡す。未指定/nullは現在の基準を使う。Layerの設定、過去Task、他案件へ自動適用しない。通常用/本番用の新しいモードは作らない。

GOBOLDはレビューの**判断基準**であり、レビューをいつ行うかとは別軸。Operation Phase 5.5の発動時期・独立reviewer・現在承認されたAC・有限枠を維持する。停止中の最終一式レビューCollectionは実装/適用/再開しない。基盤権限、実際の拒否、漏洩/破壊リスクを緩めない。

## Reviewerへ渡すものと検証順

通常/GOBOLD共通の[本人原要求と現在Goalの照合](requirement-review.md)を先に適用する。本人の原要求原文/実出典・その後の明示変更を入力へ保持し、現在Goal自体の目的逸脱、核心動線の喪失、未実装処理の試験者による手作業代行を検査する。Goal/Task書換えやA/完了のみから核心放棄を推定せず、正当な本人変更・目的を保つ縮小を許容する。原文不足はGoal完成未検証として独立Task/先行可能工程と分ける。

成果物の現版/snapshot、元Goalとsuccess_criteria、対象Taskのdescription・全AC、最小利用/学習導線、許可/禁止範囲と選択出典、必要な既存検証を渡す。進め方の判断に関係する既存成果/未達、roadmap・Task依存、工程別の承認範囲、予算/停止条件も該当箇所だけ渡す。作成者の会話履歴・実行ナラティブ・推奨結論は渡さない。依頼を「この案が整合しているか」だけに狭めず、下記のGoalへの経路検討も明示する。入力不足は不明として示し、先行可能/既承認を推定で補わない。導線は現在の承認済description/ACから読み、GOBOLDだからといって既存ACを削除/置換しない。ACが本番機能を要求しているなら勝手にモックへ縮小せず、未達を事実として返す。

1. 現案を追認する前に、Goalへ向かう最短の利用/学習導線かを独立に問い、既存証拠を再利用する小さい代替経路が有効なら、到達結果・追加作業/費用・条件/不足で現案と比較する。代替案数や特定結論は固定しない。利用者が最初の操作から目的の結果へ到達する最小の方法を先に試す。既存のプロンプト/規約/画面で成立するなら、それを第一候補とする。
2. モックの動作レビューでは、現在のモックで許されたダミー/固定値を使い、実行結果・操作trace・テスト出力等で導線を確かめる。文言だけの合格、全件Passの作り込み、動かしていない「No findings」は不可。ダミー使用と実接続/本番未検証を短く区別する。Goal/GAP・計画のread-onlyレビューでは保存資料の根拠を照合し、新しい製品動作/本人受入を検証したとは報告しない。
3. より小さな方法で不要になる前提・依存・調査を見つけ、「削る」へ分類する。必要な現在ACを削らない。不要な本番要件・確認待ち・管理文書をモックの必須条件として追加しない。
4. 実行証拠と各ACの達成/未達を返す。未達を黙って除外しない。未検証は合格にせず、利用可能な方法で検証を補う。

## 正式完了と、進められる工程を分ける

現在Taskの全AC達成による正式完了と、次MVPの計画、限定試作/実装、提供/本人受入の開始条件を別々に照合する。前Taskの完了条件を、他の許可済み作業すべての実行依存へ拡張しない。元AC未達・blocked・未確認を保持したまま進められる工程があればP3の進行提案を返す。

レビュー対象の計画成果物のACと、参照元の製品/TaskのACも分ける。計画資料が整合していても製品/元Goalを完了にせず、製品の未達だけを理由に、独立した計画成果物のACまで未達にしない。

ただし既存roadmap/Taskがその工程の開始依存を明記している場合は保持する。計画先行も自動許可ではない。例えば既存技術証拠から次MVPの仮計画を作れる場合でも、feedback反映後の正式再計画ACは未達のまま。実装開始が本人受入/feedbackに依存しているなら、仮計画を実装許可へ転用しない。実装先行を提案する場合は、必要な依存変更判断を示して実行を保留する。安全/認可/保存保全の実阻害は維持し、未達を残すだけで越えられるとは扱わない。

条件付き案は、既承認で今できる部分、変更判断/別許可が要る部分、最小条件と資料根拠を短く示す。旧予算・期限・停止を再発効せず、他Task/Layer/過去レビューの設定も変更しない。不要な復元・過剰な開始条件・管理作業・同じ再承認の反復は「削る」へ返す。実際に必要な依存や必須検証は削らない。新しい計画帳票/Task/承認ゲートは要求せず、既存の短い報告に含める。

## 指摘の三分類と停止条件

| 分類 | 扱い |
| --- | --- |
| 今直す | 現在の最小導線を成立させるため必要な重大支障、重大な漏洩/破壊リスク、実際の権限不足だけ。P0〜P2として現行ゲートを適用 |
| 後回し | 最小導線を壊さない改善・一般的な完成度・将来拡張、未達を保持した工程先行等の進行提案。P3で非阻害。新Task/計画を必須作成しない |
| 削る | 小さい方法で不要になった仕様・依存・調査・管理作業。P3で非阻害。許可内で除去する案を返し、既存AC/他案件/実権限は勝手に変更しない |

「今直す」には対象箇所、再現/観測した根拠、具体的影響、次のいずれかの理由、**最小解除条件**を必須にする。

- `user_flow_failure`: 現在の承認済モックの主要導線が実際に成立しない。どの操作から何ができなくなるかを示す。現在ACの必須結果が欠ける場合もここへ具体化する。
- `leak_or_destruction`: 重大な漏洩/破壊につながる具体的な経路がある。仮想の将来リスクだけでは付与しない。
- `missing_permission`: 現在必要な操作について実際の拒否/不足した権限がある。別経路での迂回案を解除条件にしない。

全AC達成、必要な検証証拠（動作がACならその動作証拠）、レビュー版一致、未解決P0〜P2ゼロが完了条件。機械の分類結果はsemanticな安全性証明ではなく、実証と独立reviewerが判断する。根拠不足/未取得のレビューは担当が同じ枠内で補い、成功扱いしない。同じ許可の再承認や開始文再送を解決策として追加しない。重大阻害/AC未達を予算内で解消できなければ具体的な残件として終了する。

「No findings」は指摘なしであり、進め方を検討していない意味にしない。重大欠陥なしでも有効な進行/削減案があればP3として残す。案がなければ現案維持の理由、入力不足なら判断未確認を既存報告に短く添える。毎回の指摘・先行案は強制しない。P3は完了阻害にせず、AC未達の正式完了を許す根拠にも使わない。

## 実案件相当の隔離回帰例

承認範囲内の「Aを選んだら続行する」モックは、固定したA回答を受けた担当がそのまま次の処理へ進む方法をまず検証する。新しい投稿API、Goal差分/計画登録、operation ID、exactly-once調査をこの導線の必須条件にしない。traceが `選択A → 既承認処理 → 結果` となることを確認し、不要となった旧依存は「削る」。実際にA後に再確認待ちとなり結果へ進めないなら「今直す」。実案件はこの回帰のために変更しない。

## 任意の読取CLI

公開版には CLI（plc_review.py）は無い。CLI を使わない場合と同じ入力を reviewer に渡す（GOBOLD選択時は既存intent/backlogからGoal・roadmap・依存・実行制約も付ける）。

補助JSONは `snapshot`、全ACを同じ順で並べた `acceptance_checks`（criterion/passed/evidence）、`findings` を持つ。GOBOLD findingsは `category`（今直す/後回し/削る）、`severity`、`location`、`evidence`、`impact`、`minimal_fix`。今直すには上の `blocking_reason`、他はP3を使う。根拠のない重大指摘を機械がP3へ降格したり、不正な報告を合格にしたりしない。
