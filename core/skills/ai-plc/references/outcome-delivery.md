# 成果単位の分解・実行・再開

InceptionのTask生成、simpleの直接Task生成、Constructionの担当指示、Operationの継続、plc-nextの案内に適用する。既存工程内で使い、新しい承認・調査・帳票・修正回数上限を増やさない。

## 選択済みの方式を先に適用する

現在Intentの `mode`、選ばれたアドオン（同梱の PM アドオンは旧い欄 `work_style` を含む。判定は `.claude/skills/ai-plc/scripts/plc_addon_select.py`。intent の `work_style` が null 以外か `addons` が空でないときだけ）、明示選択された `dev_style`、品質extensionsと実選択出典を先に照合する。該当する既存正本の工程順・必須成果物・入力/判断・承認・検証・保存条件を制約にして、その中で成果スライスを切る。モード指定を通常方式へ戻したり、工程/文書/本人判断をまとめて省略したりしない。未選択の方式は追加適用せず、未知/衝突は既存の選択契約に従う。

- 同梱の PM アドオン（旧い欄 `work_style: aipm` も同じ）は [AIPM正本](../../aipm-guided/SKILL.md)のコース・19必須文書・13工程フォルダ×2と、Init→persona→problem→validation→solution→story→archiveの依存を保持する。各段階の判断可能な成果をスライスにできるが、必須工程/形式・実仮説検証・本人回答・保存ゲートを省略/代行しない。
- `mode: platform_builder` は [既存正本](../04-operation/platform-builder.md)のProduction Skill生成→量産→Evalまでを全体の残範囲に含める。一件の試作成功でdirectの完了へ変換しない。
- 任意DevStyleは [既存接続契約](../extensions/contract.yaml)を保持する。共通分解からprivate入口を新規探索せず、未選択/非開発はprivate読取0。auto/forceも既存の許可/停止の適用であり、方式の必須条件を解除する理由にしない。

## 分解する

1. **依頼の終点を読む。** 既存intent.yamlの本人原文/出典・明示変更・Goal/SCを読み、誰が何を使い、どの結果を得たら依頼が成立するかを決める。[原要求照合](requirement-review.md)に従いAI要約を原文にしない。未取得は明記し、既存Contextの実出典を必要な範囲で確認する。Intentの新設・複製・Goalの縮小を再開の条件にしない。
2. **最終Goalへ近づく小さなアウトカムで段階を切る。** 最終Goalは依頼全体、スライスはその途中で「利用者が新しく何を使える/判断できるか」が変わる到達点、Taskはそれを実行する単位と区別する。大きい依頼は、対象の少量化・利用場面・判断可能な範囲・通常運用への拡張などから、複数段階のスライスと依存をまず検討する。全依頼を一Taskへまとめることを既定にしない。前段の成果を後段で使い、各段階に確認できる価値の増分を持たせる。Devは小さい対象の通常利用経路、ビジネスは限定した判断/業務が成立する段階で切る。調査→設計→実装やファイル数だけで区切らない。
   必要な確認・調査・設計・実行・検証は各スライスの手順へ含める。原則は小さいスライスを一Taskにできる粒度とし、責務/依存上複数Taskが必要なら同じ段階の共通到達点をdescription/ACで束ねる（新しいSprint/Layer/必須帳票を作らない）。選択モードの独立工程/Task・SubLayer条件は保持する。元依頼全体の完成を各TaskのACに繰り返して巨大化させない。
3. **大きすぎず、小さすぎないか確かめる。** 一段階で多数の場面/対象・長い実装が要る、成果を確認して次へ反映する機会がない場合は、成立する利用/判断の範囲をさらに絞る。逆に前後で利用/判断状態が変わらない細片は隣のスライス内の手順へ戻す。ただし選択モードが求める独立成果/工程や4項の正当な調査は維持する。必須の安全/品質や核心処理を後回しにして見かけの価値を作らない。短い依頼で増分を切る意味がない場合は一Taskでよく、その理由を示す。固定の段階数・Sprint期間・追加の予算/修正上限は設けない。
   descriptionに「対象範囲・前段から新しく成立する利用/判断状態・経路・内包調査・次段階」を、ACにそのスライスの確認方法/証拠、guardrailsに本当の許可/判断境界を含める。既存欄を使い、段階の並びと全体未達を分解表の説明へ含める。段階ごとの成果が元Goalにどうつながるかを確認し、部品の完成だけをアウトカムとしない。
4. **独立調査を判断する。** 調査/提案/比較そのものが依頼成果なら正当な独立Task。実装等が終点の場合でも、重大な未知の結果で方式・可否・実施判断が変わり、成果Task内で解消すると無駄/危険が大きい場合は独立調査を許す。その場合はdescription/ACに「何を決めるか・調べ終える条件・結果別の後続実装/実施先」を書く。分かった後は結果を後続へ渡し、同じ調査を繰り返さない。後続が未採用なら条件付き候補に留め、勝手に開始しない。
5. **全体への到達を確認する。** 各SCに対応するTask/既存成果/残件を照合し、最初の一件だけで全体をcompletedにしない。全件展開・運用・非露出等が依頼範囲なら残Task/未達として保持する。承認済み既存Task/完了実績は保持し、変更が必要なら差分Re-Inceptionと既存承認範囲で扱う。

適用例は目的を決めるテンプレートではない。終点は毎回Intentから取る。

| 最終Goal | アウトカムの段階例（大きい依頼の場合） | 各段階の証拠/残範囲 |
|---|---|---|
| Dev: 業務階層を利用する | 一件の所属/親子/根拠を正規保存・通常画面確認 → その一件の変更/訂正も通常経路で反映 → 採択した残対象へ展開し継続利用 | 各段階の実操作/readback/画面結果と全体未達。該当する認可/非露出は最初から満たす |
| Dev: 自動蓄積を継続利用する | 一種類の通常相談で自動保存→次相談参照が通る → 変更/訂正/忘れて後も正しく参照/非参照 → 必要な残入口/利用場面へ展開 | 小さい段階でも自動蓄積/通常参照の核心を残し、手動編集/特別指示で代行しない |
| ビジネス: 広い導入判断 | 代表的な一業務で候補の適否を判断できる → 他の重要業務/総費用/移行条件も判断できる → 全体の導入範囲・推奨/残条件を判断できる | 各段階で使える比較案と根拠。調査は内包。本人の採択/契約は依頼/許可範囲のみ |
| ビジネス: 複数部門の会議準備 | 最優先論点の選択肢を議論できる → 部門間依存/資源競合も判断できる → 会議全体の議題/事前資料/判断点を使える | 内容上の議論/判断が前進する段階。単なる調査/清書で切らず、開催/招待/送信を足さない |
| ビジネス: 複数申請の処理 | 代表一件の準備/許可された申請が成立 → 条件の異なる対象も正しく処理 → 依頼範囲の処理/受付確認が揃う | 未承認送信は停止し準備済みと送信未達を分離。安全/規程を後段へ先送りしない |

## 小さい修正の調査と検証環境

再現・期待結果・変更範囲・安全条件が揃い、修正判断を変える重大な未知が無ければ、選択済み方式の必要な計画承認と実変更許可を照合し、最小パッチと必要な回帰検証へ進む。追加調査は「結果によってどの修正/実施判断が変わるか」と終了条件を既存Taskへ短く示し、有効な既存証拠を再利用する。調査自体が依頼成果の場合や、方式/可否を変える重大な未知の独立調査は「分解する」4項に従い保持する。

検証環境の不具合は対象バグと分け、短い切り分けで必要な検証経路と不足を確認する。環境の根因究明を広げるのは、明示的な環境修理依頼、又は必須検証に必要で現在の許可・有限枠内に収まる限定復旧の場合だけ。環境が対象バグの一部だと示す観測があれば、修正判断を変える範囲の調査を行う。環境修理を元成果の暗黙の前提にせず、別件として扱う判断は本人に戻す。発見だけで新Taskを作らない。

検証できないACは未確認/blockedと残条件を保持し、成立済み実装・検査・レビューの同版証拠と分けて保存する。AC削除、証拠なしのPASS、実アクセス拒否の迂回はしない。許可内の独立作業は依存を照合して続ける。レビューのblockingは対象差分又は今回必要なAC・承認済み計画/既存不変条件への具体的影響と最小解除条件を示す。既存severity/profileの選択条件、独立検証、全AC達成と未解決P0〜P2ゼロの完了ゲート、選択方式の必須条件、既存予算/停止は維持する。

## 止まった後に続ける

終了・中断・判断待ちで、同じbacklogの既存Task/result/refactoring_logへ次を短く残す。複数Taskをまたぐ場合は任意の `backlog.resume_context` 一つへまとめてもよい。専用ファイル・新Task・記録自体のレビューは不要。

- 現在Intent/Task版と原要求の所在、今回成立した成果と証拠の所在
- 現在スライスの到達点/未完操作、次スライスの新しいアウトカムと依存、Goal/SCの未達・未確認（少量の成功後に残る全体範囲を含む）
- 再利用する調査結果/判断/途中成果と有効条件、まだ不明な点
- 次の具体操作/Taskと得る証拠、本当に待つ判断・許可・実際の拒否/エラー
- 既存execution_contract/execution_budget/停止条件の参照

**次の会話が読む結果は、保存してから終える:** 処理を終える・止まる前に、次の会話が続きに使う結果（持ち越し・未判定の候補・到達点）を決まった記録の場所へ保存する。決まった場所は、Layer では上の backlog の Task/result・refactoring_log（または resume_context）、アドオンが結果の保存先を宣言しているときはその場所（[addon-seam.md](addon-seam.md)「結果の保存先」）。保存できなかったら、結果の先頭に「保存できなかった：<保存先>・<エラー>」と出し、完了・済みと書かない。再開する側は、続きを始める前に宣言された保存先を最初に読む。保存先がまだ作られていない（初回）ときはその旨を1行出して進めてよい。権限やエラーで読めないときはその旨を出し、「前回の続きは無い」として進めない。

再開時は**現在の正本を優先して**この記録を照合し、未達成果への次の操作から進む。保存された開始文/要約/承認フラグを現在の許可としない。[有効実行判定](../../plc-auto/references/execution-record.md)を保持し、稼働中のTaskを二重起動しない。新しい会話だからという理由でCollection・全域調査・完了Taskをやり直さない。期限切れ/対象変更/反証/入力不足がある結果だけ、理由を記録して必要範囲を再確認する。

方式の選択/版と必須工程の現在位置も引き継ぐ。スライスの完了や会話の変更を、AIPM等の次の必須工程を飛ばす根拠にしない。既存Taskはこの粒度へ自動統合/分割/AC変更せず、許可された差分Re-Inceptionで扱う。

DB未接続・機能未実装・許可不足・観測されたアクセス拒否は別の状態。拒否は実試行の操作/対象/エラー出典がある場合だけ報告し、試していない接続を「拒否」と断定しない。許可された確認はTask内で行い、本物の拒否は別経路で回避しない。

送信・申請・契約・実データ登録等の未承認操作はその境界で停止し、準備済み内容・未達操作・必要な判断/許可を残す。許可範囲内の独立作業は続ける。停止/取消/期限や品質ゲートを成果志向で解除しない。Task全終端・試作成功と元依頼の全体達成を分ける。


## AIPM成果から開発方式へ渡す場合

AIPM併用の開発は、InceptionでAIPM成果Taskと開発Taskを先に分解し、OperationでAIPMの必須成果/ストーリーマップ/判断/保存を完成させてから最初の開発インタビューへ渡す。上流待ち開発Taskの登録は可能、起動は不可。技術的な質問という理由でInceptionを飛ばさず、AIPMの本人判断を開発質問で代行しない。登録と同版上流照合は02-inception/04-operationの契約を使い、別管理基盤や分解承認の反復を増やさない。
