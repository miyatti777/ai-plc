# plc-next（次の選択肢の復元）

論理名: SKL_plc_next。読取専用で案内を返す入口。`plc-consult`を挟まない。

**アドオンの前置判定（持ち込みのアドオンがある Layer だけ）:** 対象 Layer の intent の `addons` に、目録（[addon-catalog.yaml](../ai-plc/references/addon-catalog.yaml)）にある同梱の件（`source: bundled`）以外の件が1件でもあるときだけ（判定関数 `.claude/skills/ai-plc/scripts/plc_addon_select.py` の `has_case_addons` とおおむね同じ。判定関数で held になる形も前置判定の側に倒す）、[addon-seam.md](../ai-plc/references/addon-seam.md) の「現在依頼の読取境界を最初に判定する」「全入口の前置条件」を最初に適用し、必要なら `.claude/skills/ai-plc/scripts/plc_addon.py` を実呼出する。addons の中身は、既に許可された intent 読取の範囲内でだけ確認する。addons の無い Layer（既定）と、同梱の PM アドオンだけの Layer（旧い欄 `work_style: aipm` を含む）では Hold 判定をせず本来の手順から始める。ただし本人が今回の依頼で「全体 no-write / trial」を明示している場合は、addons の有無によらず書込前に止めて確認する。

## 入力と対象

- `/plc-next`：このスレッドの直前の結果・直前に扱ったProject/Layerを対象にする。
- `/plc-next <Layerパス or L-ID> [Task ID]`：明示対象を優先する。
- 対象が一意なら聞き直さない。IDはintent.yamlのトップレベル`scope_id`と照合し、Documents/やWorkspace/内の写しを除く。複数候補・対象不明の場合だけ、候補を最大3件に絞って1問確認する。Registryは読取照会のみ。別スレッドや最新更新案件を勝手に対象にしない。

## 読んで照合する

1. RUL_plc_session（.claude/rules/ai-plc-session.md）§7.0・7.4〜7.6・9.1と、RUL_plc_adaptive（.claude/rules/ai-plc-adaptive.md）§5〜6を読む。有効なauto/forceがある場合だけsession §10・10.1とそこで参照する契約を読む。提示された/goal例や古いログだけで有効と推定しない。
2. 直前の結果（Next Action、未回答の質問、実行・中断・検証の証拠）と対象の`intent.yaml`（Goal/AC、status、説明設定、制約）、`backlog.yaml`（Task状態・依存・AC・output・construction・guardrails・execution_budget）、`context.yaml`を必要な範囲で読む。開始先の判断に必要な成果・Agent定義・親Layerだけ追加で読む。
3. 実行中／未着手／承認待ち／保留・停止／完了を区別する。承認は対象・版・操作範囲と本人の指示を照合し、通常工程への委譲と未委譲の別判断を分ける。期限・費用・消費量の不明は不明のまま。既存の停止条件、累積予算、取消・paused/cancelledを保つ。矛盾する状態や証拠不足は明示し、完了・実行可能と推定しない。
4. [成果単位の分解・実行・再開](../ai-plc/references/outcome-delivery.md)を読み、現在Intentの原要求/明示変更と成果証拠、Goal/SC未達、再利用できる調査/途中成果と次操作を照合する。resume_context等は参照として使い現在正本で確かめる。Task全終端・一件成功だけでGoal完成にせず、単なるセッション変更を再調査/Re-Collectionの理由にしない。原要求の保存欄/実出典を引き継ぎ、Intentを再作成しない。

## 次の案を決める

**既存Next Actionが今も有効なら復元を優先する。** 同じ対象・版・依存・権限・期限で成立する選択肢ID、内容、おすすめ理由、開始文を再提示する。一部の項目だけ欠けていればそこだけ補う。実行/読取案の正式入口が欠けていれば内容を保って適合する入口を補い、工程停止だけを理由にした終了案は有効と扱わない。失効した案は失効理由を示して現状に合う案へ直す。対象版の変わらない未回答の承認質問は原文を保ち、別質問にすり替えない。

欠落時は次の基準で具体的な案を作る。工程を案内するときはその正本SKILL.mdを読み、実在する入力形式と開始先を確認する。

| 状態 | 案内すること |
| --- | --- |
| Collection済・分解未了 | `/02-inception`。simpleでStage 2省略可能なら共通の省略規定に従う開始先を示す。仮Taskは作らない |
| 計画済・構築が必要 | construction.tasksのうち必要なAgent定義が無いTaskへの`/03-construction`。既存backlogにconstruction欄が無ければadaptive §6の互換規定を使う |
| 承認済・実行可能Taskあり | 依存解決済みで未着手の具体Taskへ`/04-operation`。優先度・Goalへの到達根拠で推奨する。`scheduled_for` が今日より後の Task は『待ち（実行時期 M/D）』として示し推奨にしない（04-operation Phase 1）。実行可能が時期待ちだけなら、最も早い時期と、その日に打つ開始文（Task 指定）を示す。 |
| 実行中 | 結果待ち・現在状態の読取確認を先に示す。同じTaskの再起動、依存Taskの先行開始は勧めない。中断が証拠で確定した場合だけ同じTaskの残範囲からの再開案を出す |
| 承認待ち | 未承認の対象版・範囲と既存の承認／修正／差し戻しを再提示する。既承認の通常工程を承認待ちに戻さない |
| 期限切れ・予算記録不備・資料不足・依存未解決 | 停止/不足と解除条件を具体化し、必要なら正式な読取入口又は資料提示の返信文。実行を再開せず、期限延長や予算リセットを含む開始文を作らない。Goal完了とは表示しない |
| Stage/Task完了・全Task終端 | Goal/SCと証拠を照合し、未達成果があればその次の正式入口を示す。スキルの「止まる」を終了案にしない。全Goal達成が確認できれば依頼完了と明記。GAPや未記録は必要な確認/記録入口、親/兄弟の続きは実在と状態が確認できた場合だけ候補にする |
| paused/deferred | 本人の保留状態・理由・解除条件を保持して示す。確認案には正式読取入口を付ける。再開先はその案件の正式手順と現在条件が確認できた場合だけ。保留をGoal達成にしない |
| cancelled | 本人の中止状態と未達を保持する。再開希望がある場合のみ[plc-project-status](../plc-project-status/SKILL.md)の中止Project用正式再開入口を案内し、再開済みとは扱わない |

新しい相談・Goal変更・再計画を必須の中継にしない。現在の証拠からBacktrackの必要性が明らかな場合だけ理由と正式な戻り先を候補にする。重い工程はsession §7.5〜7.6に従い、判定不能の本工程に⭐を付けない。

## 返して止まる

**現在の実行記録を優先:** [Goal・Operation・Resume共通判定](../plc-auto/references/execution-record.md)のTask/版/承認・現在状態を読み、古い文書の開始文を現行Taskへ上書きしない。読取の現版と前後の版照合は担当が行い、本人へ別担当の共有規約更新完了証拠を必須提出させない。実書込の競合/排他は書込開始時に確認する。この入口の読取専用と「返して止まる」は保持し、委譲済み工程への新しい承認ゲートにも、実行開始の許可にも変えない。

冒頭に「Next Action（再提示／補完）」と対象・現状を短く示し、同じ回答に以下を出す。

1. **選択肢表**：`選択肢 | アクション | 選んだ後に起きること`。実行/読取案には正式Stage/plc入口、具体対象、得る成果を付ける。具体的で異なる現実的な案と、妥当なおすすめに⭐。無意味な案や未完Goalの「ここで終了」で行数を埋めず、既存案のIDは保持する。
2. **推奨理由**：直前の結果・依存・Goal/AC・停止条件などの根拠。推奨できなければ⭐なしと理由・再開条件を示す。
3. **開始用プロンプト**：実行/読取案には現在地に適合する実在Stage/plc入口とLayer/Task、対象範囲・得る成果・既存制約を埋めたコピペ文を同時提示する（コードブロックにしない）。結果待ち・承認回答・本人保留取消・真の完了は操作入口を無理に付けず、状態を保つ具体的な返信文を全文で出す。入口不明は不足を示し、仮コマンド・パス・Task・承認は作らない。共通session §7.4を正とし空欄や「開始文なし」にしない。
   再開案には「再利用する成果/調査の所在・未達終点・次に行う具体操作/得る証拠・本当の待ち/許可境界」を必要な範囲で含める。業務申請等の準備済みと実送信未達を区別し、案内だけで権限を増やさない。

今回の案内処理をここで止め、ユーザー向けNextは先の成果への選択を示す。対象が一意なら新しい選択質問・必須待機を追加しない。既存の人の判断待ちを復元する場合だけsession §9.1を適用する。同じ未回答UIを重複発行せず、現在のツール用途・待機制約を守る。保存を求める共通規約と読取専用が衝突する場合はこの呼出しでは保存せず、同じ原文・対象版・未回答・再開先と保存不可の理由を会話に残す。UI受付や既定選択を承認にしない。

**この呼出しでは次工程・実案件操作・checker・外部同期を起動せず、ファイル/Registry/native Goal/認証設定を変更しない。** 次の選択肢を表示する依頼を、実行許可・承認解除・予算延長・Goal変更と解釈しない。有効なauto/forceや委譲済み通常工程の権限は維持し、「再承認不要」と明記する。この案内入口の読取専用を、呼出し後の既承認作業への新しい承認ゲートにしない。
